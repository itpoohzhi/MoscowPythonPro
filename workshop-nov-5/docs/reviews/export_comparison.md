## 1. Нарушения слоёв и контрактов в vibe-версии

Слоёвую дисциплину vibe-версия формально не нарушает: sqlalchemy в эндпоинте нет, HTTP-код сопровождает вызов сервиса строкой `content + media_type`, что допускает транспортный слой. Все реальные дефекты — **нарушения контрактов и защитные проблемы**:

### 1.1. Неформализованный контракт ответа (нарушение п. 3.1 / 3.2 AGENTS)
- Роутер объявляет `response_class=Response`, но не имеет ни `response_model`, ни DTO: контракт — неявная строка CSV, колонки которой живут в константе `CSV_EXPORT_HEADER` **внутри сервисного слоя** (`app/services/link.py:52-60`). Контракт «утёк» под транспортный слой и виден только чтением кода.
- OpenAPI не отражает формат ответа — `/docs` бесполезен для потребителя этого эндпоинта: контракт не может быть проверен схемой, а его ломание не ловится валидатором.

### 1.2. Отсутствие валидации входа и OOM-риск
- В эндпоинте **нет ни одного параметра**: клиент не может ни ограничить выборку, ни отфильтровать статусы — «страницы» отсутствуют как понятие.
- `LinkService.export_links_csv(limit=10_000)` — захардкоженный silent truncation: `LinkRepository.list_all(limit=limit)` молча обрезает выборку. Клиент не получает сигнала, что ссылки усечены (ни `total`, ни nextPage-маркера).
- Вся таблица (вплоть до 10 000 строк) сериализуется одним `StringIO` в RAM — неступенчатая выгрузка деградирует до OOM на больших объёмах.

### 1.3. Нет обратной совместимости фильтров
- Нельзя отличить «disabled» от «expired», нельзя искать по подстроке URL — типовые эксплуатационные сценарии потребуют дублировать выгрузку и фильтровать уже на клиенте.

### 1.4. Слабый слепок качества тестами
- `test_export_vibe.py`: 3 сценария (строки, пустая база, disabled-флаг). Нет проверок границ, нет попыток невалидного ввода (они непригодны — валидации нет), нет проверки усечения на `limit`.
- Тест фиксирует формат CSV по заголовкам — то есть контракт воспроизводится тестом, но не схемой (двойная ответственность: тест обязан «знать» заголовки).

### 1.5. Отсутствие стоп-условий по скилу `fastapi-feature`
- Поля в CSV **переименуются только физически** — изменение заголовков в `CSV_EXPORT_HEADER` ничем не защищено (схемы нет), поэтому изменение контракта не ловится ни на этапе PR, ни на этапе runtime.

## 2. Преимущества pro-версии по скилу `fastapi-feature`

Реализация проходила по фазам скила (слепок → DTO → Red-Green → Repo/Service/Router → DoD):

### 2.1. Формализованный контракт EARS
- `ExportProResponse` (`total`, `limit`, `offset`, `items`) и `ExportProLinkItem` в `app/schemas/export.py`; строгий `StrEnum` `ExportStatus` (`active`/`disabled`/`expired`).
- `response_model=ExportProResponse` — контракт валидируется Pydantic v2 с `ConfigDict(from_attributes=True)`, виден в OpenAPI, охраняется схемой (изменение формы ответа = падение тестов на этапе PR).

### 2.2. Разработка по Red-Green
- Тест `test_export_pro.py` создан **первым** и падал с ожидаемым `404 Not Found` на целевом маршруте (подтверждено). Только после этого — послойная реализация: `repositories/list_pro` → `services/export_links_pro` → тонкий роутер.

### 2.3. Серверная пагинация и границы
- `limit: Annotated[int, Query(ge=1, le=1000)]`, `offset: Annotated[int, Query(ge=0)]`; нарушение границ → явный `422` (протестировано сценариями `test_export_pro_validates_pagination_bounds`).
- Одновременно `limit ≤ 1000` исключает OOM: в RAM всегда страница, не вся таблица.

### 2.4. Фильтры и безопасность
- Фильтр статуса через строгий enum (неизвестный статус → `422`, не SQL-инъекция).
- Поиск `search` (≤100 симв.), `ilike` по `target_url`/`short_code`, параметризованный SQLAlchemy (`f"%{search}%"`), без конкатенации SQL. **Замечание (не блокер):** метасимволы `%`/`_` в `search` интерпретируются как wildcard; риск трактуется как низкий, т.к. операция read-only и только чтение по `ilike`.

### 2.5. Чистое деление слоёв
- Репозиторий: только SQLAlchemy (`Select[tuple[Link]]` типизирован, pyright — 0 ошибок); фильтры изолированы в приватный `_pro_filters()`.
- Сервис: сборка DTO (`model_validate`), логгирование экспорта.
- Роутер: только валидация `Annotated[Query]` и передача kwargs в сервис — запрещённых импортов (`sqlalchemy`, модели) нет.

### 2.6. Сохранение старых контрактов
- `POST /api/v1/links`, `GET /{short_code}`, `GET /api/v1/links/{short_code}/stats`, CSV-экспорт vibe — не изменены. Слепок `tests/characterization/` остался зелёным (5 passed).
- Новых полей в старые схемы не добавлялось — риск обратной совместимости = 0.

### 2.7. DoD скила (все Exit 0)
| Проверка | Результат |
|---|---|
| `uv run ruff check .` | All checks passed |
| `uv run basedpyright` | 0 errors, 0 warnings |
| `uv run pytest -q` (полный, включая слепок) | все зелёные |
| `uv run pytest tests/integration/test_export_pro.py -q` | 8 passed |

8 сценариев против 3 у vibe: пустая база, порядок «новые первыми», disabled-фильтр, expired-фильтр (TTL=1s), поиск (регистронезависимый), пагинация, границы `422` (limit/offset), невалидные `status`/`search`.

## 3. Вердикт приёмки

| Версия | Вердикт |
|---|---|
| `export_vibe.py` | **Отклонено для новых интеграций.** Хранится в репозитории как legacy-контракт (защищён characterization-тестами, потребители сохранены). Кандидат на будущий safe-refactoring: вынести контракт в схему, добавить пагинацию. **Не удалить** — внешние потребители CSV-выгрузки обязаны продолжать работать. |
| `export_pro.py` | **Принято.** Реализовано по профессиональному скилу `fastapi-feature`: контракты зафиксированы схемами, границы защищены валидацией с 422, слои чисты, DoD (ruff, basedpyright, pytest) зелёный, слепок и старые контракты не тронуты. |

**Профессиональный итог:** vibe-версия показывает «работает, пока данных мало»; pro-версия решает эксплуатационные вопросы (OOM, усечение, отсутствие фильтров, слабый тест), что и является разницей между вайб-кодингом и инженерной моделью разработки фичи.
