# Архитектурные правила проекта (`linksvc`)

Этот справочник дополняет `.agents/AGENTS.md` и задаёт правила границ слоёв, проектирования C4 и безопасной работы с внешним I/O для сервиса `linksvc` (FastAPI, SQLAlchemy 2.0 async, PostgreSQL 17, Alembic, Pydantic v2).

## 1. Слои и разрешённые зависимости

Направление зависимостей строго сверху вниз:

`app/api/v1/endpoints/` → `app/services/` → `app/repositories/` → `app/models/`

- **Транспорт (`app/api/v1/endpoints/`):** принимает HTTP-запрос, валидирует вход через `app/schemas/`, вызывает сервисный слой и мапит доменные исключения в HTTP-статусы. Импорт `sqlalchemy`, `app/models/` или прямые запросы через `AsyncSession` запрещены.
- **Сервисы (`app/services/`):** бизнес-логика, доменные инварианты, проверка безопасности URL (`app/core/security.py`), управление транзакцией. Импорт `fastapi.Request`, `fastapi.Response`, `HTTPException` запрещён.
- **Репозитории (`app/repositories/`):** изолируют SQLAlchemy-запросы (`select()`, `insert()`, `update()`). Репозиторий вызывает только `flush()`, но не `commit()` и не `rollback()`.
- **Модели (`app/models/`) и схемы (`app/schemas/`):** ORM-модели не утекают в HTTP-ответы напрямую; наружу отдаются только Pydantic-схемы (DTO) с сохранением обратной совместимости полей и HTTP-статусов.
- **Контроль:** границы слоёв проверяются детерминированным линтером `uv run python tools/verify_techlead_gate.py`, а карта модулей лежит в `docs/module-map.md` и `docs/INDEX.md`.

## 2. Правила диаграмм C4 (Mermaid)

Для архитектурного документа рисуются ровно **два уровня** — не больше и не меньше:

1. **C1 — System Context:** система `linksvc`, пользователи/клиенты и внешние системы (PostgreSQL, аналитика, внешние consumers).
2. **C2 — Container / Component:** основные контейнеры и слои приложения (`API → Service → Repository → DB`) с направлением потоков данных и протоколами.

Оформление: только рендеренный Mermaid (`flowchart LR` / `flowchart TB`), без ASCII-арта, не более 7–9 узлов на диаграмму.

## Захват данных из динамических источников

Если задача читает данные из внешнего или динамического источника (пагинируемый API, поток событий, растущий лог, браузерная страница с ленивой догрузкой):

- **Один снимок/`read` может быть неполным.** В проекте фиксируй стратегию захвата явно: один снимок или аккумуляция при проходе по курсору/страницам.
- **Независимый сигнал полноты обязателен.** Подтверждай, что данные не обрезались, через внешний независимый сигнал: счётчик `total` / `X-Total-Count` / `Content-Length` / курсор `next_cursor is None` / контрольная сумма — а не по принципу «вернулось непусто и без ошибки».
- **Защита памяти (anti-OOM):** для больших выборок из БД и экспорта используй курсорную/keyset-пагинацию или потоковую отдачу (`StreamingResponse` + `stream_scalars()`), а не `scalars().all()` в оперативную память.

## Таймауты и watchdog для I/O, который может зависнуть

Любой внешний I/O (HTTP-вызов через `httpx.AsyncClient`, запрос к БД, запуск подпроцесса, работа с очередью или браузером) способен зависнуть без исключения:

- **Таймаут на каждом шаге цепочки:** задавай явные `connect` / `read` / `write` / `pool` таймауты и общий deadline операции (`asyncio.timeout(...)`), а не только таймаут первого вызова.
- **Защищённый cleanup в `finally`:** закрытие соединений (`close()`, `aclose()`, `disconnect()`, `terminate()`) тоже оборачивай в ограниченный таймаут, чтобы зависший cleanup не подвешивал воркер.
- **Ограниченные ретраи:** повторяй только идемпотентные операции с экспоненциальным backoff и жёстким лимитом попыток.
