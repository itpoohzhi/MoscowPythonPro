# Стандарты тестирования (`linksvc`)

Этот справочник определяет пирамиду тестов, правила изоляции, запрет на бутафорские тесты и критерий реальной проверки результата.

## 1. Пирамида тестов проекта

1. **Characterization Tests (`.agents/skills/characterization-tests/SKILL.md`):** фиксируют текущее фактическое поведение сервиса до правок.
2. **Unit-тесты (`tests/unit/`, `.agents/skills/tests-unit/SKILL.md`):**
   - Тестируют бизнес-логику сервисов (`app/services/`) и чистые модули (`app/core/security.py`).
   - Используй **In-Memory Fake-репозиторий** вместо хрупких `AsyncMock`/`MagicMock`, чтобы проверять реальное состояние и ветвления, а не только факт вызова мока.
   - Целевое время прогона unit-слоя — `< 1 с`, покрытие ветвлений (`--cov-branch`) по тестируемым модулям — близко к 100%.
3. **Integration-тесты (`tests/integration/`, `.agents/skills/tests-integration/SKILL.md`):**
   - Выполняются против **реального PostgreSQL 17** из `docker-compose.yml` (никаких подмен на SQLite и моков репозитория).
   - Проверяют реальные HTTP-коды, JSON-контракты, транзакции, ограничения БД (`UNIQUE`, `FK`, `CHECK`) и изоляцию между тестами.

## 2. Обязательные требования к тестам

- Строгая типизация (`from __future__ import annotations`, аннотации параметров и `-> None`), прохождение `uv run ruff check .` и `uv run basedpyright`.
- Полная изоляция: каждый тест сам готовит свои данные и не зависит от порядка запуска других тестов.
- Покрытие ветвлений (`[tool.coverage.report] fail_under = 85` в `pyproject.toml`): действует правило **только вверх** — снижать порог или удалять `assert` запрещено.
- Покрывай не только happy path, но и граничные случаи: SSRF-векторы (`127.0.0.1`, `169.254.169.254`, `10.x`, `172.16.x`, `192.168.x`, `::1`, `file://`, `javascript:`), коллизии `short_code`, истёкший `expires_at`, неактивные ссылки, 404/409/410/422.

## Зелёный прогон ≠ корректно

Успешный `pytest` / `ruff` / `basedpyright` сам по себе **не доказывает**, что фича или багфикс работают в реальности:

- **Защита от тихих отказов:** для операций парсинга, извлечения, трансформации, экспорта и SQL-агрегаций проверяй результат на реальном входе (включая вход, который воспроизводил баг) и сравнивай с **независимым эталоном**, а не по критерию «непусто и без исключения».
- **Независимость эталона:** метрика вида «сравнили результат с тем же урезанным захватом» остаётся зелёной при потере данных. Для динамических/пагинируемых источников сверяй полноту с независимым сигналом (ожидаемый счётчик, метаданные, число записей в БД).
- **Живая проверка:** после фикса бага или новой фичи убедись, что сценарий проходит без моков ключевой логики и на реальной БД.
